# PaperQuery Chat 功能优化记录

## 背景

当前 Chat 模块已经具备多模型问答、论文临时上传、多文件 RAG 对话和流式输出能力，但从实际使用体验看，用户对“当前模型是谁”“当前对话绑定了哪些论文”“历史对话是否被保存”“模型切换后上下文是否连续”等关键状态缺少明确感知。

本文档用于记录 Chat 功能的现有不足、修改建议、已完成修复和后续可用于简历描述的项目亮点。

## 当前发现的问题

### 1. 模型切换缺少明确反馈

现状：
- 前端通过 `src/stores/modelStore.ts` 保存当前模型。
- `src/views/chat/components/ModelBox.vue` 切换模型后只更新下拉框显示。
- 页面不会弹出提示，也不会在聊天流中插入“已切换到某模型”的系统消息。

问题：
- 用户无法确认本轮请求是否真的使用了新模型。
- 切换 DeepSeek、Kimi K3、OpenAI 后，界面反馈太弱。
- 如果模型请求失败，用户容易误判为“系统没有响应”。

建议：
- 切换模型后触发 `ElNotification` 或 `ElMessage`，提示“已切换至 Kimi K3”。
- 在聊天记录中插入一条轻量系统消息，例如“当前模型已切换为 Kimi K3，后续回答将使用该模型”。
- 每条 AI 回复旁边显示实际使用的模型名称，避免后续复盘时混乱。

### 2. 当前对话绑定论文不明确

现状：
- Chat 请求通过 `src/stores/documentList.ts` 收集当前上传文件的 `documentID`。
- 后端 `/chat/mulit_file_chat_generate_flow` 根据 `uid` 做多文件检索。
- 页面只展示上传文件列表，但没有突出提示“当前对话正在基于哪些论文回答”。

问题：
- 用户不知道当前问答到底绑定了哪一篇或哪几篇论文。
- 用户无法判断是“已经指定论文”还是“没有指定论文的普通聊天”。
- 当上传多篇论文后，缺少当前检索范围提示，容易误解回答来源。

建议：
- 在聊天页顶部增加“当前论文上下文”区域。
- 单篇论文时展示：`当前对话论文：论文名.pdf`。
- 多篇论文时展示：`当前对话已绑定 3 篇论文`，并以标签列表显示论文名。
- 未指定论文时展示空状态：`尚未选择论文，当前为普通模型对话`。
- AI 回复中可以展示引用来源，例如命中文档名、页码或片段摘要。

### 3. “导出”按钮目前没有实际功能

现状：
- `src/views/chat/content/components/HeaderArea.vue` 中存在“导出”按钮。
- 当前没有绑定导出事件，也没有对应的导出逻辑。

问题：
- 空按钮会降低用户对系统完成度的信任。
- 用户点击后没有反馈，会被认为是功能损坏。

建议：
- 短期：删除“导出”按钮，避免误导。
- 中期：如果保留导出，应支持导出当前聊天为 Markdown / PDF。
- 导出内容应包含：模型名称、绑定论文、问答时间、用户问题、AI 回答、引用来源。

### 4. 缺少右侧历史聊天记录面板

现状：
- 当前聊天记录主要保存在前端运行时状态中。
- 页面右侧没有展示账号过往聊天记录。
- 用户刷新或重新登录后，很难回到之前的问答上下文。

问题：
- 不利于论文阅读过程中的长期研究追踪。
- 用户无法按论文、时间、模型回溯历史对话。
- 对“个人知识库助手”的定位来说，历史会话是核心能力之一。

建议：
- 在右侧增加“历史会话”面板。
- 按时间倒序展示当前账号的历史聊天。
- 每条历史记录展示：标题、绑定论文、使用模型、最后更新时间。
- 支持点击恢复上下文。
- 支持按论文筛选历史会话。

### 5. 切换模型后的上下文连续性需要明确设计

现状：
- 前端发送请求时会携带 `context`，该值来自 `src/stores/memory.ts`。
- 切换模型后，新模型仍会收到同一段 conversation memory。
- 理论上可以继续理解上下文，但不同模型对同一段记忆的解释能力和风格不完全一致。

风险：
- 模型 A 生成的摘要记忆可能不适合模型 B。
- 切换模型后，如果不插入提示，用户不知道上下文是否仍然生效。
- 多模型混用时，历史记录里缺少“本轮由哪个模型回答”的元数据。

建议：
- 模型切换时不清空上下文，但需要明确提示“已保留当前对话上下文”。
- 每条消息记录保存 `model` 字段。
- 后端会话摘要增加当前模型信息，便于排查问题。
- 如果用户主动开启新聊天，则清空 memory 和当前消息列表。

## 已完成的技术修复

### Chat 交互体验优化

本轮已完成：

- 删除 Chat 顶部无实际功能的“导出”按钮。
- 在 Chat 顶部展示当前论文上下文：
  - 未绑定论文时提示“尚未指定论文，当前为普通模型对话”。
  - 绑定论文后展示当前对话关联的论文文件名。
  - 多篇论文时展示绑定论文数量和文件标签。
- 模型切换时触发明确提示：
  - 页面弹出“已切换至某模型”的提醒。
  - 聊天流中插入系统消息，提示已切换模型。
  - 明确提醒“切换模型无可避免可能导致回答准确率降低，需要结合论文来源核对”。
- 对模型切换后的上下文做压缩处理：
  - 保留最近若干轮关键对话。
  - 保留当前绑定论文名称。
  - 将压缩后的上下文写入 memory，降低跨模型切换时的上下文漂移和幻觉风险。
- 为 AI 回复增加模型标签，便于用户确认每条回答来自 DeepSeek、Kimi K3 还是 OpenAI。
- 增加右侧历史会话面板：
  - 按当前账号保存本地会话快照。
  - 展示会话标题、模型、更新时间、绑定论文数量和论文名。
  - 支持点击历史会话恢复消息内容。
  - 支持开启新聊天并清空当前上下文。

### Kimi K3 调用参数修复

问题：
- Kimi K3 接口报错：`invalid temperature: only 1 is allowed for this model`。
- 原因是后端创建 Kimi 的 `ChatOpenAI` 实例时没有显式设置 `temperature`。

处理：
- 在 `PaperQuery_Backend/core/llm/LLM.py` 中为 Kimi 普通调用和流式调用都设置 `temperature=1`。

效果：
- 避免 Kimi K3 因温度参数不合法导致流式输出中断。
- 多模型切换时，Kimi K3 可以按自身 API 约束正常调用。

### 流式输出异常兜底

问题：
- 后端流式接口内部异常时，前端容易表现为空白或卡住。

处理：
- 在 `PaperQuery_Backend/core/backend/router/router_llm.py` 的流式输出逻辑中增加异常捕获。
- 当模型调用失败时，通过 SSE 返回可读错误信息。

效果：
- 用户能看到“模型调用失败”的明确提示。
- 调试时可以更快定位是模型参数、API Key、代理还是服务端接口问题。

### Library 文档向量化链路修复

问题：
- Library 上传 PDF 后，页面长期显示“排队中”。
- 原因不是上传失败，而是上传接口只负责保存文件和写入数据库，真正的论文解析、摘要生成、向量入库需要后台 `vector.py` 独立运行。
- 本地 Windows 环境下，ChromaDB 默认会把 ONNX embedding 模型缓存到用户目录，曾触发 `.cache/chroma` 权限错误。
- 后台日志中直接打印完整论文摘要 prompt，包含数学符号和中文内容，在 GBK 控制台下可能触发编码异常，导致向量化任务中断。

处理：
- 在后端 `.env` 中增加 `CHROMA_ONNX_CACHE_DIR`，将 ChromaDB ONNX embedding 模型缓存迁移到项目目录。
- 在 `main.py` 和 `vector.py` 的 ONNX embedding 初始化中读取该缓存目录，避免依赖用户目录权限。
- 在 `vector.py` 中增加任务异常兜底，处理失败时将文档状态回滚为“排队中”，避免永久卡在“处理中”。
- 将论文摘要阶段的完整 prompt 打印改为长度日志，避免 Windows 控制台编码导致后台任务崩溃。

效果：
- 已将测试论文 `2509.21655v2.pdf` 处理到完成状态，生成 56 条向量。
- Library 页面刷新后应显示“完成”，View 和问答功能应在向量化完成后再开放使用。

### Reader 问答助手稳定性修复

问题：
- View 页面里的问答助手使用 `/chat/generate_flow` 进行单篇论文 RAG 问答。
- 如果文档仍处于“排队中/处理中”，用户提前进入 View 页面会导致问答没有可检索的论文向量上下文。
- 前端原本用正则解析 SSE chunk，但浏览器可能把一个 JSON 事件拆成多段，导致解析失败并出现空白 AI 气泡。

处理：
- Library 的 `View` 按钮改为仅在文档状态为“完成”时可点击。
- 小问答的 SSE 解析改为缓冲式解析，按 `data: ...\n\n` 事件边界解析流式输出。
- 请求失败时将可读错误写入机器人消息气泡，避免用户只看到空白响应。

效果：
- 降低用户误入未完成论文问答页的概率。
- 提升 Reader 问答助手对流式半包、网络失败、后端异常的可观测性。

## 建议的后续实现任务

### P0：提升可用性

- 删除无功能的“导出”按钮。
- 模型切换后弹出提示。
- 模型切换后插入系统消息。
- 在聊天页显示当前绑定论文列表。
- 未绑定论文时给出明确空状态提示。

### P1：增强会话管理

- 增加右侧历史聊天记录面板。
- 新增后端聊天会话表：`chat_sessions`。
- 新增后端聊天消息表：`chat_messages`。
- 每条消息保存 `session_id`、`role`、`content`、`model`、`document_ids`、`created_at`。
- 支持按账号查询历史会话。

### P2：增强论文问答可信度

- AI 回复展示引用论文名。
- AI 回复展示引用页码或文本片段。
- 多论文问答时标注答案主要来自哪篇论文。
- 当检索不到相关论文内容时，明确提示“当前论文中没有找到依据”。

### P3：完善工程质量

- 给多模型调用增加统一配置层。
- 为不同模型维护参数白名单，例如 Kimi K3 固定 `temperature=1`。
- 为 SSE 流式接口增加错误事件格式。
- 增加前端状态持久化，避免刷新后丢失当前会话。

## 可写进简历的项目亮点

- 设计并优化多模型论文问答模块，支持 DeepSeek、Kimi K3、OpenAI 等模型在同一 Chat 界面内动态切换。
- 基于 FastAPI + SSE 实现大模型流式响应，降低用户等待感，并补充异常兜底机制提升可观测性。
- 构建多文件 RAG 对话链路，前端上传论文后将文档 ID 传入后端，由 ChromaDB 检索相关论文片段并注入模型上下文。
- 识别并修复 Kimi K3 模型参数兼容问题，为特定模型配置 `temperature=1`，解决模型接口 400 错误导致的流式回答中断。
- 规划 Chat 体验优化方案，包括模型切换反馈、当前论文上下文展示、历史会话面板、无效功能清理和会话可追溯设计。
- 从产品体验角度补齐“当前模型、当前论文、当前会话、历史记录、错误状态”的用户感知闭环。

## 推荐的简历表述版本

PaperQuery 是一个面向论文阅读与知识库管理的 AI 助手系统。我负责优化 Chat 问答模块，支持多模型切换和多论文 RAG 对话。项目使用 Vue3 + Pinia 构建前端状态管理，FastAPI + SSE 实现后端流式响应，结合 ChromaDB 完成论文片段检索与上下文注入。在调试过程中定位并修复 Kimi K3 模型参数兼容问题，并规划了模型切换提示、当前论文上下文展示、历史会话追踪和流式错误兜底等体验优化，提升了系统的可用性、可解释性和工程稳定性。
